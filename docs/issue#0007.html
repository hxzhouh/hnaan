Implementation Notes

Issue #7 — Reduce request CPU within Workers Free limits — 2026-11-16

Design Decisions

Cache the compiled public UI dictionary, regular expression and client script by the exact stored dictionary value. Database settings are still read on every request, so CMS edits invalidate the cache immediately.

Resolved public query results (256 entries) and compact English summaries (2 versions) are reused per database revision. A fresh revision is read per request; SQLite/D1 and MySQL triggers change it atomically with public source or translation writes. No pending database I/O is shared across requests. Configuration/UI is read once per render; detail rows are still fetched directly.

Deviations

Legacy article/case/service list queries now omit content and wap_content. Detail records and explicit body queries retain those fields. Current templates use bodies only for details, pages and contact blocks.

Tradeoffs

The HTML policy has no CSS-value allowlist. Keeping inline CSS verbatim avoids a PostCSS parse for every legacy span while preserving tag, attribute and URL-scheme filtering. Plain text without markup/entities skips HTML parsing. Already-English HTML chunks skip the 500-key replacement regex.

Open Questions

Initial production audit observed 157 desktop and 8 mobile resource-limit responses. Local sample CPU reductions are approximately 31–55%, with fewer unused database characters. The second sweep still found 96 desktop and 5 mobile failures, so a further versioned snapshot fix was required. Local warm sample requests now typically use 1–3ms of CPU; this is not a Cloudflare SLA. The final acceptance criterion is a fresh production sweep with zero failed responses, not the local timing alone.
